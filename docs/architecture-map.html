A · CLI + session engine

The local agent runtime that orchestrates OpenCode sessions on a user's machine. Yargs-based CLI, the interactive TUI session loop, the session processor that turns LLM streams into typed events, the tool registry, MCP clients, plugin host, and the Effect-based service infrastructure (instance state, event bus, projectors) — backed by a Drizzle/SQLite session database.

Scope-local patterns

  • Service + Layer everywhere. Every subsystem extends Context.Service and provides an Effect layer; cross-references in project/bootstrap.ts stitch them together in deterministic order.
  • InstanceState + ScopedCache. Per-workspace state (LSP servers, file watchers, snapshots) is auto-cleaned on workspace disposal — prevents leaks across multi-project servers (effect/instance-state.ts).
  • Schema-first errors and events. Schema.TaggedErrorClass and Schema.Struct give every public payload a runtime validator (see permission/index.ts, cli/error.ts).
  • Lazy + forked startup. Heavy init (LSP spawn, reference index, file watch) is forked into background fibres so the first prompt is unblocked.

Open questions

  • How is subagent execution modelled — how do nested sessions inherit permissions and pass context back?
  • Where does the Workspace entity live relative to Project and Session? packages/opencode/src/control-plane/ hints at a remote concept that wasn't sampled.
  • How is plugin-hook ordering and error handling defined — can hooks veto a tool call?

Scope-local patterns

  • Branded schema IDs. Every domain concept is a Schema.String.pipe(Schema.brand(...)) with optional static constructors.
  • Schema.Class for domain objects. Info records are simultaneously runtime values and codecs (Schema.Class<Info>).
  • Protocol ↔ Route separation. Wire-format mapping (Protocol) is decoupled from deployment / auth (Route), avoiding duplication across providers.
  • Stream-based LLM I/O. LLMClient.stream() and tool-runtime.stream() return Effect Streams for cancellation, backpressure, composability.

Open questions

  • Persistence: core defines interfaces but not storage bindings — bindings live elsewhere (Scope A SQLite, Scope D Drizzle/PlanetScale).
  • Are custom protocols plug-in extensible, or is the set of six fixed?
  • How are plugins discovered — from disk, npm, or dynamically at runtime?

Scope-local patterns

  • IPC bridge. Renderer ↔ main via typed window.api exposed in preload (preload/index.ts).
  • Connection abstraction. A single ServerConnection union handles http / sidecar / ssh / wsl, with createSdkForServer() minting an SDK per backend.
  • Event coalescing. The server SDK batches sync events with frame-based flush (~16ms) and stream yield (~8ms) to avoid render churn.
  • Theme system. oklch colour math generates neutral / alpha scales; applyTheme injects CSS variables at runtime.
  • Persisted state. Electron via electron-store; app via @solid-primitives/storage wrapping localStorage.

Cross-cutting patterns

Patterns that recur across multiple scopes — the architectural backbone of the monorepo.

  • Effect-TS as the runtime fabric. ABDE  Services are Context.Service + Layer — the CLI (effect/instance-state.ts), the core / llm packages (core/src/plugin.ts), the stats ingest server (stats/server/), and the internal HTTP recorder / Drizzle libs (effect-drizzle-sqlite/) all share the same DI / Layer / Stream vocabulary.
  • Schema-first domain modelling. ABD  Effect Schema / Zod define every public payload — branded IDs (core/src/agent.ts), tagged errors (opencode/src/cli/error.ts), and Zod DTOs in the console (console/core/src/account.ts). Codecs are the source of truth, not types.
  • OpenAPI-generated SDK is the contract. CDE  sdk/openapi.json is generated by the CLI and consumed by the desktop / web app (app/src/context/server-sdk.tsx), the Slack bot (slack/src/), and external integrations.
  • Drizzle ORM. ADE  Same ORM, different backends: local SQLite for the CLI session DB (session/session.sql.ts), PlanetScale MySQL for the console (console/core/src/schema/), and an internal Effect adapter that holds them together (effect-drizzle-sqlite/src/).
  • SolidJS + SolidStart for every web surface. CD  The desktop app (app/src/app.tsx), the console dashboard (console/app/), and the enterprise share app (enterprise/src/) are all SolidStart, sharing primitives from packages/ui/src/.
  • Bun runtime end-to-end. ADE  The CLI (opencode/src/index.ts), release scripts (script/publish.ts), stats services, and even the base container layer (containers/bun-node/) run on Bun. Turborepo coordinates the workspaces (turbo.json).
  • Projector / event-stream pattern. AB  Typed events (core/src/event.ts) are published to a PubSub bus (opencode/src/bus/index.ts) and projected onto session views (server/projectors.ts) consumed by the SDK over the wire.
  • Plugin / hook extensibility. ABE  Hook spec defined in core (core/src/plugin.ts), invoked by the CLI plugin host (opencode/src/plugin/), packaged for third parties as packages/plugin/.

Aggregate open questions

  • Persistence boundary. Core defines storage interfaces; the CLI uses SQLite / Drizzle and the console uses PlanetScale / Drizzle — but the bridge for sharing sessions to the cloud (Scope D's share endpoints) isn't fully traced.
  • Subagent execution. Agent config supports nested subagents but the spawn / context-propagation flow isn't directly visible from the sampled files.
  • Zen gateway state machine. Where rate-limit state actually lives (Redis vs. ModelTpsRateLimitTable) and how it coordinates with billing isn't fully resolved.
  • Plugin loading. Discovery (npm vs. local dir vs. registry) and hook precedence / error handling are still open.
  • SDK versioning. v1 ↔ v2 split — deprecation timeline and migration story for downstream consumers.
  • Reconnection semantics. Desktop multi-server switching and remote SSH disconnects — how subscriptions resume.
